今回は**ホームの集計とデータ取得の改善**を対象にします。具体的な計画は以下です。

**目的・実装方針**

- 初期表示では共通情報と今月のサマリーを取得し、ホーム用の全明細取得をなくします。
- 月変更時は、対象月をDBで集計し、ユーザー別・合計の収入、支出、収支だけを返します。
- 清算は全期間の未清算共有明細をサーバーで計算し、金額・人数別の配分・対象件数を返します。清算履歴は現在の最新20件を維持します。
- 初期表示、更新ボタン、ワークスペース切替、保存後更新、カテゴリ同期の各経路を見直し、ホームで全件取得が発生する経路を外します。
- 取引一覧の画面・検索・並べ替え・全件取得方式は維持します。一覧を開いたときに従来データを取得する接続調整だけを含め、ページ分割は別タスクにします。
- 今回はキャッシュや事前集計テーブルを追加せず、既存の取得・計算処理とインデックスを活用します。

**受入条件**

- **AC-01**：ホームの初期表示・更新・月変更で、全明細や清算対象IDの配列をブラウザへ返さない。
- **AC-02**：日本時間の月単位、清算済み・未来日付を含む対象範囲、共有費の端数配分を維持し、従来と同じ収支になる。
- **AC-03**：月変更が清算対象に影響せず、清算額・共有費配分・履歴・清算完了操作が従来どおり動く。
- **AC-04**：明細保存・取込・清算後にサマリーを更新する。保存後の取得失敗は「保存済み・表示未更新」と扱う。
- **AC-05**：月やワークスペースを素早く切り替えても、遅い応答で表示が戻らない。
- **AC-06**：取引一覧・取込・設定・既存の集計画面が継続して動作する。

清算のサーバー処理量は未清算件数に応じて増えますが、ブラウザへ送るデータは集計結果に限定します。

**実施・検証**

1. 承認後、Issue・専用branch/worktree・Intentを作成します。
2. API・画面の取得処理・関連設計書と回帰テストを更新します。
3. 件数を増やしたデータで取得範囲と応答量を確認し、月境界・端数処理・保存後更新・通信失敗・応答逆転を検証します。
4. 別Agentレビュー、lint・型チェック・全自動テスト・build・CloudブラウザQA、CI・専用Previewでの確認を終え、PRをReadyにします。merge後は既存Actionsが稼働と資源cleanupを確認します。
