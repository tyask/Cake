# 設計・実装原則

新しい機能も変更する機能も、以下の観点を設計時から確認する。
対象の規模と関係する処理に適用し、必要な境界を小さく保つ。
仕様の正本は[基本設計](design.html)・[詳細設計](detail-design.html)、開発・検証・PRの手順は[開発手順](development-workflow.md)に従う。

## 1. 責務とデータの流れを先に決める

- UIは入力と描画、controller/hookは取得・更新・通知と応答の採用条件、HTTP境界は認証・入力parse・応答変換、サービスは業務条件、
  store/repositoryはSQLを担当する。
  純粋な業務計算にHTTP・DB・画面状態を持ち込まない。
  既存の境界を使い、単純な機能に層ごとのファイルや汎用基盤を機械的に増やさない。
- ライブラリは実行場所に応じて `lib/client/`・`lib/server/`・`lib/shared/` へ置く。
  運用スクリプトとテストは用途・対象領域にまとめ、依存を追加するときは[配置と依存境界](detail-design.html#architecture)を確認する。
  `npm test` の境界検査を維持し、共有定義へサーバー処理やUI・運用処理を持ち込まない。
- 入力途中の値、サーバーで確定した値、表示から導く値の所有者を決める。同じ確定データを複数箇所で独立更新せず、派生値は確定値から計算する。
- ボタンや自動保存を起点に、送るpayload、分岐条件、呼ぶAPI/サービス、DBで読む・書く対象、応答の反映先を追えるようにする。
  複数の取得範囲や保存後分岐がある場合は詳細設計にデータフロー図と操作表を置き、ローカル入力だけを変える操作と通信する操作も区別する。

参照：[Dashboardのデータフロー](detail-design.html#dashboard-data-flow)、
[HTTP境界](../lib/server/handlers/app-handlers.ts)、[用途別サービス](../lib/server/services/app-service.ts)。

## 2. 同じ業務規則は入口によらず共有する

- 分類・状態・action・表示精度などの有限値は定数一覧や名前付き定数から型を導出し、schemaと表示ラベルも整合させる。
  入力上限や正規化を画面・CSV・APIへ複製しない。
  共有モジュールはブラウザでも使える依存に限定する。
- 手入力、CSVプレビュー、登録APIで共通の分類・割合・ルール判定を使う。入口ごとに既定値が異なる場合は引数などで明示し、共通化で仕様差を消さない。
- クライアントの検証成功を信用境界にせず、サーバーでも入力と現在の権限・所属を確認する。型定義だけで未知の外部値を正当化しない。
- APIでは日時のミリ秒など、保存・比較に必要な精度を保持する。
  円・タイムゾーン・表示桁の整形は表示境界の共通formatterに集め、Intlの同じ設定は再利用する。
  入力欄の変換と表示書式は分ける。
- 別実装が必要なTS/SQLの業務計算は共通fixtureで結果を照合する。丸めの位置・対象・未一致時の結果まで契約に含める。

参照：[分類値](../lib/shared/domain-values.ts)、
[入力schema](../lib/shared/schemas/domain-schemas.ts)、
[ルールと割合](../lib/shared/expense-splits.ts)、[表示書式](../lib/shared/display-formatters.ts)、
[TS/SQL共通fixture](../tests/shared/fixtures/default-rule-cases.ts)。

## 3. 保存・再取得・遅延応答を一つの流れとして設計する

- draftと保存成功を確認した基準値を分ける。
  trimや割合mapの順序などを正規化して比較し、同値では送信しない。
  複数の保存契機は共通の保存制御へ集約し、送信直前の値で判定する。
- 再取得や一括操作の前に必要な保存を完了させる。保存失敗時は入力とエラーを保持し、古いGET結果で編集中の値を上書きしない。成功した確定値を基準へ反映してから次の保存へ進む。
- workspace・画面の切替、保存後のrevision、要求順序を考慮して応答の採用条件を決める。
  古いworkspaceの応答を現在の画面へ混ぜない。
  同じworkspaceでの表示反映と、現在タブへの通知の条件も区別する。
- ブラウザで応答を破棄しても、開始済みのサーバー更新が取り消されるとは扱わない。重複更新・再試行・同時実行の整合性はサーバー/DB側でも保証する。

参照：[保存制御](../lib/client/autosave.ts)、[保存待ち更新](../lib/client/transaction-refresh.ts)、
[応答採用条件](../lib/client/dashboard-requests.ts)。

## 4. 共通UIの標準動作を共通部品で保証する

- 同じ目的の選択肢・入力制約は共通部品で標準提供する。すべての利用箇所で必要な機能を、呼出元ごとのopt-in指定にしない。
- 表示する選択肢と操作できる条件は分ける。参加人数・権限・保存中などの条件で無効にする場合も、共通の選択肢と状態が一貫するようにする。
- 操作対象以外の行・選択・未保存入力・既定値を意図せず変えない。プレビュー内の変更とサーバー登録のタイミング、保存値と表示用の丸めを明確にする。
- 共通部品を変更したら全呼出元を検索し、それぞれの状態とデータ反映を確認する。PC/mobile、追加/編集など意味の異なる経路を、変更に応じて検証する。

参照：[割合の共通入力](../components/split-editor.tsx)、[取込画面](../components/import-panel.tsx)、
[定期支払い画面](../components/recurring-payments-panel.tsx)。

## 5. 反復処理では共通準備と個別判定を分ける

- ルールの無効除外・優先順の整列などは、同じデータを処理するリクエスト/バッチ内で一度準備し、各要素では先頭から最初の一致を採用する。元配列と同順位の順序を保持する。
- 繰り返す完全一致の所属判定はSet/Map、一度の走査で導ける一覧・件数は共通結果を使う。部分一致や優先順の検索を完全一致Mapへ置き換えない。
- ReactのuseMemoは入力が変わる単位で準備を再利用する場合に使い、依存値を揃える。
  正しさをキャッシュの存続に依存させず、ユーザー/workspaceをまたぐ可変グローバルキャッシュを作らない。
- 性能の説明ではソート・走査・ファイル本文読込・通信など対象を示す。計算量の改善と実測時間の改善を区別し、時間を主張するときは同じデータ・初期状態・実行条件で測る。

参照：[準備済みルール判定](../lib/shared/expense-splits.ts)、[一覧計算](../lib/shared/transaction-list.ts)、
[フィルタ](../lib/shared/transaction-filters.ts)。

## 6. 用途に必要な取得と集合更新を使う

- 更新APIの判断に画面用全データを取得しない。用途別の列・対象・取得範囲を用意し、ルールなど条件付きで必要な情報だけ読む。同じ処理内で参加者や設定の再取得を繰り返さない。
- 明細ごとのDB呼出しや集約・更新は集合で処理できるか確認する。ネットワーク往復だけでなく、SQL関数内のループやstatement数にも件数に比例する増加がないか確認する。
- 軽量応答で未取得項目を空配列に置き換えない。部分応答の型と同一workspaceへの併合条件を明確にし、更新応答で確定値を反映するか再取得するかを選ぶ。
- migrationは適用台帳を一度取得し、未適用本文だけを読む。初回の所有権・原文・接続先検査など、安全性に必要な確認は省略しない。

参照：[取得範囲](../lib/client/bootstrap.ts)、[明細用業務処理](../lib/server/services/transactions.ts)、
[清算store](../lib/server/stores/settlement-store.ts)、[migration実行](../scripts/db/setup-db.mjs)。

## 7. 複数対象の更新を原子的に確定する

- 単件と複数件で同じ業務操作は共通経路にまとめる。最新権限、全対象の存在・所属・更新可否、計算前提を確認し、一部だけ成功しないようにする。
- 更新と同じTransaction内で必要なロック・再検証を行う。
  事前取得だけで確定せず、清算などの計算結果が依存するsnapshotを照合する。
  ロック順と対象順を揃え、DB制約も使って二重処理を防ぐ。
- 履歴・関連行・本体更新・再採番は必要な単位で一緒に確定し、失敗時は全体をrollbackする。競合・再試行時の結果を定義し、不要な行やworkspaceを更新しない。
- 適用済migrationの原文を書き換えず、新しい番号のmigrationを追加する。
  公開中の旧版との切替期間を含めて互換性を考える。
  migration本体と適用台帳の記録も一緒に確定する。

参照：[清算のロック・snapshot](detail-design.html#domain)、
[DB更新store](../lib/server/stores/app-store.ts)、[migration設計](detail-design.html#database)。

## 8. 維持する挙動と運用経路までレビューする

- 変更前に維持する契約を挙げる。
  例は優先順・同順位順、部分一致、保存割合、最後一度の丸め、選択やdraft、認可、全体rollbackである。
  変更に関係する境界値・未一致・失敗・競合・応答逆転を、観測できる結果で検証する。
- テストは利用者の挙動・業務契約・DB不変条件に向ける。
  低影響の削除や文書変更に、実装の形だけを写すテストを増やさない。
  自動テストと実Preview、画面移動と業務更新は区別して報告する。
- 運用コマンドの入口を重複させない。
  置換時はnpm scripts・workflow・コード・文書の呼出元を検索し、使われている経路は移行してから整理する。
  正式receipt・認証・保護・資源の照合を迂回する別経路を作らない。

参照：[開発・レビュー・検証手順](development-workflow.md)、[コマンド定義](../package.json)。
