5. 認証・セッション詳細設計

Googleモード

  • テスト認証が無効なときGoogle Providerを登録。
  • Googleの確認済みメールとProviderのメールが一致し、app_usersに有効な通常ユーザーとして事前登録されていることが必要。
  • メールは前後空白を除去して小文字化。別名メールの統合は行わない。
  • GoogleのSubjectではなく登録済みの内部IDをJWT subに保存。

テストモード

  • AUTH_MODE=testかつVERCEL_ENV !== production。
  • Credentials Provider test-loginを登録し、固定のA/Bキーを解決。
  • 固定IDとメールの組合せだけを自動登録/有効化。保存済みの表示名は維持。
  • 常に非管理者。通常アカウント二人の上限から除外。Productionでは強制無効。

ログインと現在ユーザー

  1. createAuthCallbacks()のsignInで登録・有効状態を確認する。Googleログインは未登録アカウントを自動作成しない。
  2. Googleログイン時のupdateRegisteredProfile()は画像URLだけを更新し、Cakeで保存した表示名を上書きしない。
  3. jwt callbackでもGoogleアカウントの有効状態を再確認して内部ID・メールを保存。session callbackでtoken.subをsession.user.idへ設定。
  4. getCurrentUser()は毎回findSessionUser(id, email)でDBを照合し、現在の名前・画像・管理者権限を返す。停止/削除されたユーザーや認証モードと異なるセッションはnull。

利用者管理

初回マイグレーションで管理者を登録する。通常の有効アカウントは管理者を含め二人まで。管理者はメールを登録し、停止済みの通常ユーザーを同じ内部IDで再有効化できる。停止は取引や所属を削除せず、既存セッションからのアクセスも無効にする。

認証・利用可否、workspace所属、管理者権限を分ける。管理APIはrequireAdministrator()で現在のDB権限を再確認し、SQLの変更条件でも管理者の有効状態を確認する。通常workspace操作はOWNER/MEMBERを区別せず所属を認可条件とする。

6. アプリケーションAPI詳細設計

共通仕様とGET

  • Runtimeはnodejs。UUID・32 byte招待トークン・SHA-256をNode Cryptoで生成。
  • POSTはactionと入力をZodで検証。SQLはNeon tagged templateで値をパラメータ化する。
  • /api/app成功はHTTP 200。GET失敗は基本401、POST失敗は基本400。UserAccessErrorは固有statusを優先し、応答は{ error }。
  • GETはgetBootstrap(user, workspaceId, scope)を実行。scope省略はfull。所属していない/不正形式の指定IDは本人の所属一覧先頭へフォールバックする。

POSTアクション一覧

action主な入力・検証更新処理・成功応答
updateProfile本人のみ。nameをtrimして1〜120文字。strict schema。DB上の本人ID・メール・有効状態を条件に名前更新。{ ok, user }。
createWorkspacename 1〜80文字、PERSONAL/SHARED。UUID生成、workspaceとOWNERを一括Transactionで作成。{ ok, workspaceId }。
updateWorkspace / deleteWorkspaceworkspace UUID・所属。更新はname 1〜80文字、削除はconfirmationName完全一致。名称とupdated_at更新、または配下をCASCADE削除。{ ok }。
createInvite共有workspace・所属、Email、本人以外、参加者2人未満。tokenのHashだけ保存、期限7日。同じworkspace/emailは再発行。{ ok, invitePath }。メール送信は行わない。
acceptInvitetoken 64文字、Hash一致・PENDING・期限内・本人メール一致・2人未満。MEMBER追加とACCEPTEDをTransaction実行。{ ok, workspaceId }。
updateWeights共有workspace・所属、現在の全参加者1〜2件、ID重複なし。整数0〜2147483647、合計は正。workspaceとmemberのデフォルトweight更新。保存済み明細の割合は変えない。{ ok }。
saveTransactionworkspace/任意transaction UUID、ISO日時、merchant 1〜240、method 1〜120、正整数円、type、参加者actor、任意class/split。新規だけ任意memo。新規はMANUALとmanual_UUID。既存は未清算行だけ更新し、既存割合の省略時は可能な限り保持。所属者別割合を検証。{ ok, transaction }は確定DB行のDTO。
saveTransactionMemostrict入力: action、workspace UUID、transaction UUID、memo最大2000文字。清算済みも更新可能。メモ・監査項目だけ更新。{ ok, transactionId, memo }。既存saveTransactionへmemoを含めると拒否。
deleteTransactionworkspace/transaction UUID・所属。未清算の対象行だけ削除。0件なら業務例外。{ ok }。
deleteTransactions / applyTransactionRules所属、transaction UUID配列1〜5000件、大小文字を正規化した重複なし。DB関数で全選択の存在・未清算を検証し、全件削除/現在ルール適用。{ ok, deleted } / { ok, applied, appliedTransactions }。
createRule / updateRule所属、merchantContains 1〜120、class、任意splitWeights/null、任意enabled。更新はrule UUID。新規はsort_order末尾、enabled既定true。共有割合nullは現在のデフォルトを利用、個人費ルールはnull。更新時に省略した割合は区分同一なら保持。{ ok }。
reorderRules所属、全rule UUID配列最大5000。DB関数で現在の全ルールとの完全一致・重複なしを確認し、sort_orderを0始まりで更新。{ ok }。
deleteRule / deleteRules所属、単一UUIDまたは重複のない配列1〜5000。複数削除は全対象の存在確認。対象workspace内だけ削除しsort_orderを詰める。{ ok } / { ok, deleted }。
bulkImport所属、fileName 1〜240、totalRows非負、items最大2000。各actor・class・割合・金額・ISO日時・外部IDを検証。PAYPAY/PAYMENT明細とbatchを同一Transactionで登録。外部ID順で登録し一致重複は省略、不一致は全体を中止。{ ok, imported, skipped }。
completeSettlementworkspace UUID・所属、最新full参照で対象明細あり。対象計算値をロック下で再照合し、履歴・関連行・settled_atを一括保存。{ ok }。
bulkImportのimportedとimport_batches.imported_rowsは、新規batch IDを持つ明細をDB Transaction内で数えた実挿入件数。重複は既存明細を更新せず、skipped = max(0, totalRows - imported)として記録する。

重複確認API

POST /api/import/duplicatesは{ workspaceId, externalIds }を受け、IDの重複をまとめて選択workspaceだけを照合する。応答は{ externalIds, transactions: [{ externalId, merchant, amountYen, source }] }。未認証は401、検証/所属/DBエラーは400。CSV原本や既存明細の全件取得は不要。

利用者管理API

Method入力・処理
GET管理者の利用者一覧。固定テストID/メールのA・Bを除外し、管理者・有効状態・作成順で返す。
POSTstrict JSON { email, name? }。Email正規化、name任意1〜120文字。通常ユーザーを新規登録/停止済み再有効化し一覧を返す。

共通API呼出と再取得

  1. postAction()がJSONをPOST /api/appし、非2xxのerrorを例外化する。
  2. run()が要求開始時のworkspace・世代を保持し、現在のworkspace向けの成功応答だけを反映する。通知はタブ世代も一致し、手動更新中でない場合だけ表示する。
  3. saveTransactionはサーバーの確定TransactionRecordを一覧へ置換/追加し、日時で並び替え、清算を再計算。saveTransactionMemoは返されたメモだけを反映。どちらも直後の全件GETを省く。
  4. その他の更新とタブ切替はrefresh()で再取得。import/settingsはmetadata、home/transactions/settlementはfull。workspace切替は常にfull。
  5. metadataは同一workspaceの取得済み明細・清算・履歴を保持して併合する。選択workspaceが変化した場合はfullを取得し直す。

画面の手動更新

  • ホーム・取引明細・清算に「↻ 更新」を表示する。ホームは指標上部、取引明細は見出し右側の追加ボタン左、清算は見出し右側。白背景・薄いベージュ枠・茶色文字、高さ44px、角丸10〜12pxとし、スマートフォンでは見出し・説明の下に文字付きの操作行を右寄せする。
  • 現在のworkspaceをfullで再取得する。画面遷移やコンポーネントの再マウントを行わず、フィルタとスクロール位置を保持する。
  • 取引明細は全行の未保存入力とメモを保存し、保存キューの完了を待ってからGETする。入力検証・保存に失敗した場合はGETせず、下書きと再試行を保持する。
  • 保存待ちから取得終了まで回転アイコンと「更新中…」を表示し、二重実行と競合する操作を抑制する。noticeで成功・エラーを通知する。
  • 開始時のworkspace・世代とタブ世代を保持し、現在の表示と一致する場合だけ応答と通知を適用する。途中でタブやworkspaceが変わった場合、元のタブへ戻っても古い処理の完了で現在の画面を置換しない。

新規明細

NewTransactionModalはPAYMENTを登録する。UI初期値は共通費と現在のデフォルト割合で、取引先ルールに一致すると区分・割合を適用する。ルール未一致もUIでは共通費を選び、利用者が区分/割合を変更した後は自動適用を止める。APIと清算計算はRECEIPTも扱うが、新規画面には種別切替を持たない。

明細編集・一括操作

  • 文字・日時・金額・割合は欄を離れるかEnterで保存。選択項目は変更時に保存。入力検証後、保存キューで順番に実行し、失敗時の下書きと再試行を保持する。
  • 取引の担当者を変更すると個人費の割合は新担当者1・ほか0に追従。共通費の保存済み割合は保持する。費用区分を新たに共通費へ変更すると現在のデフォルト割合を使う。
  • 割合は%と円入力を切替可能。円表示は最大剰余法で配分し同率時は参加者順、合計を整数円に一致させる。円入力は分担金額を重みとして保存する。
  • メモは空文字で削除可能、改行/空白を保持し最大2000文字。blurまたはCtrl/⌘+Enterで専用保存。清算済み行はメモだけ編集できる。
  • 列を絞り込んでも未清算行の選択を保持する。編集・保存・エラー中の行は条件外になっても表示を維持。一括操作の前に未保存の変更を保存し、確定した取引先と担当者へルールを適用する。
  • 一括削除/ルール適用は選択全件の存在と未清算をDBで確認し、対象の一部だけを変更しない。ルール未一致は個人費へ戻る。適用済み明細の確定値を応答し、編集Stateにも反映する。

ルール編集

有効なルールを上から評価し、取引先の部分一致が最初に成立する一件を使う。文字・割合はblur/Enter、区分・デフォルト利用・有効状態は即保存。追加は末尾、ドラッグまたはスペース/上下キーで並び替え、選択したルールをまとめて削除する。操作キューは並び替え・削除と行編集を直列化し、失敗した入力や構造操作の再試行を保持する。ルール変更だけでは保存済み明細を変更しない。

清算計算

calculateSettlement(members, transactions): SettlementResult | null

  1. メンバーがちょうど2人でなければnull。未清算のSHARED明細だけを抽出し、0件ならnull。
  2. 対象actorの所属、正の安全整数金額、各明細の保存割合を検証する。
  3. 支払いを正、受け取りを負として正味共通費を計算。各明細の金額に、その明細の先頭参加者割合を掛けた分数をBigIntで正確に合算する。
  4. 全明細を合算した先頭参加者の負担を一度だけMath.round相当で丸める。負の0.5も正の方向に丸め、二人目の負担は正味共通費から先頭負担を引く。
  5. actual = ownPayments - ownReceipts、balance = actual - target。負balanceの人が支払い、正balanceの人が受け取り、送金額は負balanceの絶対値。
  6. 差額0ならpayer/payeeのID・名前はnull、金額0。対象明細があれば0円の清算完了も可能。
targetTransactions = SHARED && !settledAt signedAmount(t) = PAYMENT ? amountYen : -amountYen netTotal = Σ signedAmount(t) firstBurden = Σ [signedAmount(t) × t.splitWeights[firstId] / Σ t.splitWeights] (exact BigInt fraction) firstTarget = round(firstBurden) (once after aggregation) secondTarget = netTotal - firstTarget actual = ownPayments - ownReceipts balance = actual - target amountYen = abs(payer.balance)

SettlementPerson.weightとweight_snapshotは現在のデフォルト割合を記録するが、計算は各明細のsplitWeightsを使用する。清算Snapshotには対象明細ごとの保存割合も含める。

清算完了と同時操作

full再取得・再計算→対象値をID順に固定→ロック・Snapshot照合→履歴・関連INSERT→settled_at更新

cake_assert_settlement_snapshot()をTransaction先頭で実行し、workspace行の更新ロックを取得して所属を再確認する。現在の未清算SHARED全明細のID・actor・type・amount・class・splitWeightsが期待値と完全一致しなければ全体を失敗させる。計算に関係しないメモ・日時・取引先・方法は照合Snapshotの対象外。

計算Snapshot・対象明細Snapshot、対象関連、settled_atを同じNeon Transactionで保存する。対象明細の追加・削除・計算値変更・先行清算があれば再確認を促す。settlement_transactions.transaction_idのUNIQUE制約でも二重清算を防ぐ。清算済みの計算値は通常更新/削除不可だが、メモは専用APIで変更できる。

同じマイグレーションでcake_assert_paypay_duplicateを作成する。ON CONFLICT DO UPDATEの条件から、競合行のロックを保持した状態で既存source・金額・取引先を検証する。一致時はfalseを返して更新・返却を省略し、不一致時は日本語の例外で取込トランザクション全体を失敗させる。

12. 例外・認可・整合性設計

分類検出・扱い
未認証・利用不可現在のDB登録・有効状態・モードを照合。一般/app GETは401、POSTは基本400、重複APIと管理APIの未認証は401。画面はログイン導線。
入力不正Zod、CSV、純粋検証関数と入力欄で確認。API error/行エラーを表示し、未保存下書きを保持。管理APIは入力の詳細を固定メッセージへ変換。
非所属・管理者以外workspace所属を確認。利用者管理は現在のDB管理者権限で確認し403。通常workspace操作のOWNER専用制約は持たない。
清算済み計算値の変更通常UPDATE/DELETEはsettled_at IS NULL条件。0件は業務エラー。bulkは全対象の未清算を確認。メモは専用保存で変更可能。
古い/欠けた一括選択DB関数で全IDの存在・未清算・参加者・現在ルールをロック下で確認。一件でも不正なら全体を変更しない。
CSV重複・衝突専用API・CSV内検証・DB UNIQUE・競合行のsource/金額/取引先検証。一致は省略、内容差は取込全体を中止。
清算対象の並行変更workspaceロック下でSnapshot一致検証。対象追加/削除/計算値変更/先行清算を検出したら全体を失敗させ、更新後の再確認を促す。関連UNIQUEでも二重清算を拒否。
ルール順序の並行変更全rule IDの完全一致と一意性をDBで検証。ルール追加/削除により一覧が変化していれば再取得を促す。
遅延応答Dashboardはworkspace世代・データrevision・GET要求IDを照合。CSV選択も要求IDで古いファイル照合結果を破棄する。
DB未設定db()は明示例外。Homeに設定案内を持つが、有効ユーザー確認にもDBを使用する。

現行コード上の権限境界

  • workspace更新は招待承認を除き所属を確認。actorは同じworkspaceの参加者であることを追加検証。
  • 招待は本人のログインメールと宛先の一致を確認し、平文tokenは保存せずSHA-256を保存する。招待承認だけでは未登録Googleユーザーの利用許可を与えない。
  • 所属者はOWNER/MEMBERによらず名称・招待・割合・ルール・明細・清算・workspace削除を操作できる。削除は名称一致と確認ダイアログを使い、再認証は行わない。
  • 利用者管理はテストユーザーを除く有効管理者のみ。管理者の停止は拒否し、停止済み通常ユーザーの再登録は既存内部IDとデータを保持。
