5. 認証・セッション詳細設計

Googleモード

  • AUTH_MODEがtest以外、またはVercel Production。
  • NextAuthのGoogle Providerを一つ登録。
  • JWTセッション戦略を使用。
  • Session Callbackでtoken.subをsession.user.idへ設定。

テストモード

  • AUTH_MODE=testかつVERCEL_ENV !== production。
  • Credentials Provider test-loginを登録。
  • testUserKeyを固定ユーザーA/Bへ解決。
  • Productionでは設定ミスがあっても常に無効。

ログイン後のユーザー同期

Provider→識別子、メール、表示名、画像URLをNextAuthへ返す。
signIn event→IDとメールが存在する場合、app_usersへUPSERT。
Session→JWT SubjectをユーザーIDとして画面・APIから使用。
API→currentUser()が未認証なら例外「ログインが必要です。」。
認証は本人確認、認可はワークスペース所属確認として分離する。更新系アクションは原則としてrequireWorkspaceMember()を通過する。

6. アプリケーションAPI詳細設計

共通仕様

  • Runtimeはnodejs。Node標準のcryptoでUUID・招待トークン・SHA-256を生成する。
  • POST BodyはRecord<string, unknown>として読み、actionと各入力をZodで検証する。
  • 成功は原則HTTP 200。POST失敗はHTTP 400、GET失敗はHTTP 401で{ "error": "メッセージ" }を返す。
  • SQLはNeon tagged templateを使い、値をパラメータ化する。

入力処理出力
workspaceId?: stringログイン必須。getBootstrap(user, workspaceId)を実行。BootstrapData。指定IDが所属一覧にない場合は一覧先頭を選択。

8. ドメイン処理詳細設計

PayPay CSV解析

parsePayPayCsv(text, rules, existingExternalIds): PayPayPreviewRow[]

BOM除去→PapaParse→必須Header検証→「支払い」抽出→行検証・Rule適用→Preview
処理仕様
必須列取引日、出金金額（円）、取引内容、取引先、取引方法、取引番号。欠落時はファイル全体を例外。
対象行取引内容をtrimした値が支払いと完全一致する行だけ。
金額カンマと前後空白を除去し、数字だけを許可。正整数でなければ行エラー。
重複既存external ID Setに含まれる行はduplicate=true、初期選択OFF。
デフォルト区分enabled ruleをpriority昇順にし、merchant部分一致の先頭を採用。未一致はPERSONAL。
日時yyyy/MM/dd HH:mm:ssを正規表現検証し、JSTとしてISOへ変換。
原本FileReaderで文字列化するだけで、CSV本文をサーバー・DBへ送信しない。

清算計算

calculateSettlement(members, transactions): SettlementResult | null

  1. メンバーがちょうど2人でなければnull。
  2. expenseClass === SHAREDかつsettledAt === nullの明細だけを抽出。0件ならnull。
  3. paymentTotal、receiptTotal、netTotal = paymentTotal - receiptTotalを集計。
  4. 先頭メンバーの目標負担をMath.round(netTotal × weight / weightTotal)で算出し、二人目は残額。
  5. 各人のactual = payments - receipts、balance = actual - targetを算出。
  6. balanceが負の人をpayer、正の人をpayeeとし、送金額はpayerの絶対値。該当者なしはID/Nameがnull、金額0。
targetTransactions = SHARED && !settledAt netTotal = ΣPAYMENT - ΣRECEIPT firstTarget = round(netTotal × firstWeight / weightTotal) secondTarget = netTotal - firstTarget actual = ownPayments - ownReceipts balance = actual - target amountYen = abs(payer.balance)

清算完了

Bootstrap再取得→対象ID固定→履歴Snapshot→関連行INSERT→明細settled_at更新

全クエリを一つのNeon Transactionで実行する。settlement_transactions.transaction_idのUNIQUE制約により、同じ明細を二重に清算しようとしたTransactionは失敗する。

12. 例外・認可・整合性設計

分類検出箇所扱い
未認証currentUser()GETは401、POSTは共通catchにより400。画面はLoginScreen。
入力不正Zod / CSV関数 / HTML制約サーバーはZod messageまたは業務messageをJSON返却。クライアントはerror表示。
非所属requireWorkspaceMember()処理を中止し「操作する権限がありません」。
清算済み編集UPDATE/DELETEのsettled_at IS NULLRETURNING 0件を業務例外へ変換。
CSV重複クライアントSet + DB UNIQUE事前に選択不可。競合時もDBでDO NOTHING。
二重清算transaction_id UNIQUENeon Transaction全体を失敗させ、中途半端な履歴・更新を残さない。
DB未設定db() / HomeHomeは設定案内、サーバー関数は明示例外。

現行コード上の権限境界

  • 既存workspaceを対象とする更新は、招待承認を除き所属確認を実施する。
  • actorUserIdは対象workspaceのmemberであることを追加検証する。
  • 招待トークンは平文保存せずSHA-256 Hashで照合する。
  • OWNER専用操作は実装されておらず、所属メンバーは名称変更・招待・重み変更・workspace削除を実行できる。
  • workspace削除前の再認証は実装されておらず、名称一致と所属のみを検証する。
上記の注意点は仕様提案ではなく、現行ソースの境界を明示したものである。権限仕様を変更する場合はAPI条件、UI表示、受入条件を合わせて変更する。
