1. 文書方針

本書は 基本設計書 を実装へ対応付ける詳細設計書であり、現行ソースコードと開発・QA運用手順を正とする。

対象

app/、components/、lib/、auth.ts、DBマイグレーション、セットアップスクリプト、単体テスト。

表記

TypeScript上の名前、HTTPのアクション名、DBの物理名はコードと同じ英字表記を使用する。

変更時の扱い

API入力、型、DB制約、計算式を変更した場合は、対応する本書の表とテスト観点も同時に更新する。

本書は実装済み挙動を記録する。基本設計にのみ存在し、まだコード化されていない仕様は詳細設計へ混在させない。

lib/server/stores/用途別SQL、DTO構築、Transaction。定期支払いの既定DB storeも含む。database・server・sharedを参照し、clientを参照しない。
lib/server/database/DB接続と接続先検査、query logging、本番host禁止集合、承認済DB fixtureの検証・生成参照。serverとsharedを参照し、clientを参照しない。services・handlerからの推移的な実行時参照も禁止する。
lib/server/preview/Preview runtime proofの入力検査、DB所有権照合と安全な応答。databaseを使い、実際のDB clientはAPI入口から受け取る。

定期支払いはlib/server/services/recurring-payments.tsに業務処理とstoreの型、lib/server/stores/recurring-payment-store.tsに既定のSQL操作を置く。APIのcomposition rootがstoreをサービスへ注入し、HTTP handlerは処理を引数で受け取る。共有schema・DTO・予定日計算はsharedに置く。HTTPで扱うUserAccessError・RecurringPaymentErrorは、認証・handler・サービスをまたぐ副作用のない定義としてlib/server/errors.tsに単一定義し、handlerから認証・DB実装への実行時依存を生まない。

lib/のモジュールはclient・server・sharedのいずれかに配置する。npm testのtests/architecture/がlib/client/と"use client"からの推移依存、shared・serverの依存方向、handler・servicesからstores・database全体への到達、アプリからscripts・testsへの参照とlibの配置を検査する。ブラウザで使う外部依存は検査側の許可一覧で管理し、Node組込み・サーバーSDK・未知の外部依存を拒否する。

検査は相対path・@/のalias、拡張子省略・index、再export、文字列literalのimport()・require()を追跡する。shared、client、handler、servicesの推移依存では、解決できないlocal参照や対象を静的に決められない動的参照を拒否する。.d.ts・.d.mts・.d.ctsの型宣言ファイルと、import type・export typeなど明示された型だけの参照は実行時の依存から除き、通常のimport・再exportは型としてだけ使用していても実行時依存として扱う。

lib/shared/paypay.tsはブラウザでCSVを解析する。純粋関数のlib/shared/settlement.tsはRepositoryでの参照・清算処理に加え、ブラウザで保存済み明細の応答を反映するときにも呼び出す。

5. 認証・セッション詳細設計

Googleモード

  • テスト認証が無効なときGoogle Providerを登録。
  • Googleの確認済みメールとProviderのメールが一致し、app_usersに有効な通常ユーザーとして事前登録されていることが必要。
  • メールは前後空白を除去して小文字化。別名メールの統合は行わない。
  • GoogleのSubjectではなく登録済みの内部IDをJWT subに保存。

テストモード

  • AUTH_MODE=testかつVERCEL_ENV !== production。
  • Credentials Provider test-loginを登録し、固定のA/Bキーを解決。
  • 固定IDとdummyメールを照合。QAはseed済みの有効状態・役割をSELECTで確認し、自動登録/再有効化/権限修復をしない。保存済みの表示名は維持。
  • 新QAは固定2人だけでAがサイト管理者・共有OWNER、Bが一般・MEMBER。現在のDB権限とQA identityを照合し、Aだけ管理操作を許可。従来ローカルは非管理者。固定A/Bは人数上限から除外し、Productionでは強制無効。

ログインと現在ユーザー

  1. createAuthCallbacks()のsignInで登録・有効状態を確認する。Googleログインは未登録アカウントを自動作成しない。
  2. Googleログイン時のupdateRegisteredProfile()は画像URLだけを更新し、Cakeで保存した表示名を上書きしない。
  3. jwt callbackでもGoogleアカウントの有効状態を再確認して内部ID・メールを保存。session callbackでtoken.subをsession.user.idへ設定。
  4. getCurrentUser()は毎回findSessionUser(id, email)でDBを照合し、現在の名前・画像・管理者権限を返す。停止/削除されたユーザーや認証モードと異なるセッションはnull。

利用者管理

初回マイグレーションで管理者を登録する。通常の有効アカウントは管理者を含め二人まで。管理者はメールを登録し、停止済みの通常ユーザーを同じ内部IDで再有効化できる。停止は取引や所属を削除せず、既存セッションからのアクセスも無効にする。

認証・利用可否、workspace所属、管理者権限を分ける。管理APIはrequireAdministrator()で現在のDB権限を再確認し、SQLの変更条件でも管理者の有効状態を確認する。通常workspace操作はOWNER/MEMBERを区別せず所属を認可条件とする。

6. アプリケーションAPI詳細設計

共通仕様とGET

  • Runtimeはnodejs。UUID・32 byte招待トークン・SHA-256をNode Cryptoで生成。
  • POSTはlib/shared/schemas/app-input.tsのappActionInputSchemaでaction別の入力を一度検証し、判別可能なunionで各分岐へ渡す。未対応actionのエラー文言を維持し、最後のnever照合で追加actionの処理漏れを型検査する。SQLはNeon tagged templateで値をパラメータ化する。
  • AppActionInputとRunAppActionをクライアント送信と共有する。workspaceを親で補完するルール操作や定期支払いでも、actionごとの必須フィールドを維持した型を使う。プロフィール・メモ専用保存と定期支払いはstrict、その他のアプリactionは余分な項目を除去する既存方針を維持する。
  • domain-schemas.tsでmerchant（trim後1〜240文字）、method（trim後1〜120文字）、amountYen（1〜2147483647の整数）、重み（0〜2147483647の整数）などを共有する。通常保存とCSV取込も金額上限を業務データのDB更新前に検証する。割合の全参加者一致・正の合計・個人費1:0は引き続きドメイン検証で確認する。
  • /api/app成功はHTTP 200。GET失敗は基本401、POST失敗は基本400。UserAccessErrorは固有statusを優先し、応答は{ error }。
  • GETはgetBootstrap(user, workspaceId, scope)を実行。scope省略はfull。所属していない/不正形式の指定IDは本人の所属一覧先頭へフォールバックする。

用途別の割合コンテキスト取得

  • 各操作はDB上の最新workspace所属を確認してから取得する。splitMembers(workspaceId)は参加者のID・重み・名前、splitRules(workspaceId)は部分一致判定に必要なルール一覧を優先順・作成日時・ID順で返す。
  • createRuleは参加者だけを取得。updateRuleは参加者とruleForUpdate(workspaceId, ruleId)を並列取得し、対象1件の区分・割合・enabledだけを読む。対象SELECTとUPDATEはともにworkspaceとrule IDで限定する。不在は更新せず拒否。区分同一で割合省略なら保存値を継承し、明示nullはデフォルト参照、enabled省略は保存値を維持する。
  • saveTransactionは既存明細かつ割合省略の場合だけ未清算の前回値を取得し、区分と割合を従来の条件で継承する。PAYMENTで、その結果の区分が未指定またはSHAREDの割合が未指定の場合だけsplitRulesとルール判定を行う。RECEIPTはルールを取得・判定しない。明示PERSONALは支払者／受取者1・ほか0を生成し、区分・割合が確定済みならルールを参照しない。どの経路でも参加者・支払者／受取者・割合の検証を実行する。
  • 明示割合で区分だけ省略された通常支払い明細はルール区分を使い、前回明細の区分を読まない。共有の支払いで割合省略時は一致するルールの割合、それ以外はworkspaceのデフォルト割合を使う。新規収入の区分未指定はPERSONAL、SHARED指定時の割合省略はworkspaceのデフォルト割合を使う。CSV取込は支払いだけを対象に参加者とルールを取得し、省略値をSHARED既定で補完する。

重複確認API

POST /api/import/duplicatesは{ workspaceId, externalIds }を受け、IDの重複をまとめて選択workspaceだけを照合する。応答は{ externalIds, transactions: [{ externalId, merchant, amountYen, source }] }。未認証は401、検証/所属/DBエラーは400。CSV原本や既存明細の全件取得は不要。

カテゴリ候補API

POST /api/import/category-suggestionsは{ workspaceId, merchants }を受け、{ suggestions: [{ merchant, categoryId }] }を返す。categoryIdは候補なしならnull。importCategorySuggestionsSchemaはworkspace UUIDと取引先1〜2000件を検証し、各取引先は共通merchantSchemaのtrim後1〜240文字の規則を使う。応答のmerchantは照会元の文字列を保持し、元の文字列が完全一致する重複だけを省略して初出順に返す。正規化で同じになる別表記は、それぞれの元文字列に同じ候補を返す。未認証は401、入力・所属・DBエラーは400。MAX_IMPORT_CATEGORY_SUGGESTION_MERCHANTSとCATEGORY_SUGGESTION_HISTORY_LIMITは共有モジュールに定義する。

候補storeは有効な本人と最新workspace所属を照合し、表示用取引先をcake_normalize_merchantで正規化する。同workspace・同正規化キーについて、PAYMENT・category_confirmed = true・同workspaceの有効カテゴリありの履歴だけを対象とし、occurred_at DESC, created_at DESC, id DESCの先頭30件を選ぶ。参加者・source・期間・清算状態は制限しない。カテゴリIDごとに明細1件を1票で数え、最多を採用する。同率は各カテゴリの最新履歴が先に来る方を採用し、親子カテゴリは合算しない。30件より古い履歴は票にも同率判定にも使わない。

取引先集合を一度展開し、正規化キーを重複除去してから最新履歴・カテゴリ別件数・採用候補を集合SQLで求める。元文字列と正規化キーの対応と、正規化キーごとの候補はMATERIALIZEDなCTEで再利用し、同じキーの別表記も最新30件の探索を共有する。storeは所属確認1回と候補SQL1回の固定2往復とし、明細行や取引先ごとのアプリDB呼出し・SQL関数内のループは増やさず、全履歴をアプリへ取得しない。応答は元の取引先とカテゴリIDだけに限定し、候補照会では明細・確認状態・監査列・取込履歴を更新しない。登録時の候補再集計や新しい未確認明細UIは設けず、通常の明細編集の確認状態処理は維持する。

取込履歴API

GET /api/import/history?workspaceId=UUID&format=PAYPAYは{ history: ImportHistoryEntry[] }を返す。importHistoryQuerySchemaが共通workspace UUIDと共有形式定義を検証する。未認証は401、入力・所属・DBエラーは400。応答はCache-Control: no-storeとし、現在の利用者の所属範囲を超えた履歴を返さない。

findImportHistory()は現在の所属を確認し、履歴SQLもmembership存在を照合する。選択workspace・formatに加えimported_by = 本人IDで絞り、created_at DESC, id DESCの最新5件を返す。相手のファイル名・総件数・登録件数を返さない。

取込者名はapp_usersから取得する。本人の登録0件の履歴も対象とする。createdAtは保存済み精度のUTC ISO文字列で返し、日本時間への変換は表示境界で行う。履歴照会は読取専用で、CSV本文・明細本文・メールアドレスは返さない。

取込明細API

GET /api/import/transactions?workspaceId=UUID&batchId=UUID&format=PAYPAYは{ transactions: TransactionRecord[], categories: Category[] }を返す。importTransactionsQuerySchemaは履歴queryの共通workspace・形式検証へbatch UUIDを追加する。未認証は401、query不正・事前所属確認の拒否・DBエラーは400。batchの不在・指定workspaceや形式の不一致・認可後の所属解除は404「取込履歴が見つかりません。」とし、全応答をCache-Control: no-storeにする。

findImportTransactions()は所属を一度確認し、続く1回のSQLで対象batchの存在、現在の明細、同workspaceのカテゴリを同じsnapshotから取得する。対象batchの選択にも本人の現在のmembershipとimported_by本人の条件を含める。他人のbatchは不存在と同じ404を返す。固定2往復とし、対象明細ごとのDB呼出しや全workspace明細の取得を行わない。

明細はworkspace_idとimport_batch_idの両方を対象batchへ結び付け、occurred_at DESC, created_at DESC, id DESCで並べる。同名ファイルでもbatch UUIDで区別する。現在の明細はSHAREDまたはactor_user_id本人だけを返す。重複再取込は元のbatchとの関連を保持し、後のbatchへ移さない。編集済みの明細は現在の保存値、削除済みの明細は対象外とする。batchが存在し現在の明細が0件の場合は200で空配列を返す。

カテゴリは旧停止済みを含め全件を返して全階層のパスを解決し、既存のtransactionRecord()・categoryRecord()でDTOへ変換する。取込時の登録件数・スキップ件数とAPIの互換性は保持する。履歴一覧・明細ポップアップにはスキップ件数を表示せず、現在の明細件数と取込時の登録件数は区別する。

応答の業務結果を受け取ると、まず操作元workspace IDと世代を現在値と比較する。不一致なら現在画面のdataへ反映せず、結果を呼出元へ返す。一致した場合は次の3経路に分かれる。

① saveTransaction＋transaction

DB → { ok, transaction } → applyTransactionUpdate → 対象明細を追加・差し替え → 共有workspaceの清算結果を再計算 → data更新。

通常は追加GETなし。確定済みの日時・金額・割合を採用する。

通常は追加GETなし。清算計算は変わらない。
③ それ以外

DB → { ok, … } → refresh → 現在タブのscopeでGET → 採用判定 → data更新。

設定枠の開閉

個人設定は「基本情報」、ワークスペース設定は「基本情報」「ワークスペースのデフォルト割合」「集計用カテゴリ」「定期支払い」「区分のデフォルトルール」「ワークスペースを削除」を縦に並べる。共通のSettingsSectionがnativeのdetails / summaryで各枠を初期状態では閉じ、見出し全体のクリック・タップ、Enter・Spaceで個別に開閉する。開閉マークは直径28pxの淡い丸背景に20pxのSVG矢印を置き、閉じているときは下、開いているときは上を向く。回転は短いアニメーションで示し、動きを減らす利用者設定ではアニメーションを行わない。マーク自体は装飾として読み上げとフォーカスの対象外とする。

開閉状態は各detailsが保持し、サーバーへの保存や永続化は行わない。本文の子コンポーネントは閉じてもunmountしないため、名前・割合・カテゴリの編集中の値、ルールの選択、保存中・失敗状態を保持する。画面を離れて再表示した場合やワークスペース切替で再マウントした枠は閉じて開始する。開閉自体ではAPIを呼ばず、定期支払いの表示時GET・日付境界の再取得と各設定の既存の保存契機は維持する。

共通API呼出と再取得

  1. postAction()がJSONをPOST /api/appし、非2xxのerrorを例外化する。
  2. run()が要求開始時のworkspace・世代を保持し、現在のworkspace向けの成功応答だけを画面のdataへ反映する。取込履歴の家計別revisionはPOST成功時に独立して更新する。通知はタブ世代も一致し、手動更新中でない場合だけ表示する。
  3. saveTransactionはサーバーの確定TransactionRecordを一覧へ追加し、既存行では専用保存で確定したメモを保持し、カテゴリはcategoryRevisionが新しい方を採用して通常項目を反映する。日時で並び替え、清算を再計算する。saveTransactionMemoとsaveTransactionCategoryはそれぞれ確定した項目だけ反映し、直後の全件GETを省く。
  4. bulkImportはPOST成功時に対象家計の履歴revisionを進める。現在のタブ・家計・世代が変わっていてもこの更新は行い、現在表示と一致する場合だけ通知する。保存後のmetadata GETで失敗した場合は、保存済みで家計情報だけを取得できなかった旨を通知し、保存結果を正常に返す。確認表は保存済みとして解除し、再送を促す登録失敗にはしない。
  5. その他の更新とタブ切替はrefresh()で再取得。import/settings/analyticsはmetadata、home/transactionsはfull。workspace切替は常にfull。
  6. metadataは同一workspaceの取得済み明細・清算・履歴を保持して併合する。選択workspaceが変化した場合はfullを取得し直す。

画面の手動更新

  • ホーム・取引明細に「↻ 更新」を表示する。ホームは指標上部、取引明細は見出し右側の追加ボタン左。白背景・薄いベージュ枠・茶色文字、高さ44px、角丸10〜12pxとし、スマートフォンでは見出し・説明の下に文字付きの操作行を右寄せする。
  • 現在のworkspaceをfullで再取得する。画面遷移やコンポーネントの再マウントを行わず、フィルタとスクロール位置を保持する。
  • 取引明細は全行の未保存入力・メモ・カテゴリを保存し、保存キューの完了を待ってからGETする。入力検証・保存に失敗した場合はGETせず、下書きと再試行を保持する。
  • 保存待ちから取得終了まで回転アイコンと「更新中…」を表示し、二重実行と競合する操作を抑制する。noticeで成功・エラーを通知する。
  • 開始時のworkspace・世代とタブ世代を保持し、現在の表示と一致する場合だけ応答と通知を適用する。途中でタブやworkspaceが変わった場合、元のタブへ戻っても古い処理の完了で現在の画面を置換しない。

金額・日時の表示と入力

幅48rem以下の取引明細では、datetime-local入力の幅を0、最小幅・最大幅をセル幅の100%にして、ブラウザ固有の日時コントロールの固有幅によるはみ出しを防ぐ。WebKitの日時表示は左寄せにし、内部編集領域の最小幅と余白を抑える。秒・ミリ秒の入力値と保存処理は維持する。

サーバーは日時をミリ秒付きUTC ISO文字列としてブラウザへ返す。明細の保存応答・full再取得の取引日時と清算日時、清算履歴の完了日時、full/metadataの招待期限では秒への切捨てを行わない。DB driverのDateは文字列化を挟まずISOへ変換する。ブラウザは表示時にJSTと秒・分の書式を適用し、日時入力・再保存ではミリ秒を保持する。DBスキーマとクエリ回数・並び順・期限判定は変えない。

DB/APIのamountYenは正の整数とtype=PAYMENT|RECEIPTを保持し、表示のために保存値を負数へ変換しない。formatCashflowは収支値を「−¥5,000」「+¥5,000」、0円を符号なしで表示する。formatTransactionAmountはPAYMENTを負、RECEIPTを正に変換して同じ書式を使い、cashflowClassは正にpositive（緑）、負にnegative（赤）、0に通常色を返す。ホーム・明細・CSV確認表・定期支払い・配分金額・集計の本人収支表で共用する。集計の共有費全体カードとカテゴリ別支出グラフ・内訳表は、通常の通貨書式で無符号・通常色を維持する。本人の月次表・ツールチップ・棒の金額ラベルは収支表と同じ符号を使う。CSVの非有限金額を「—」にする補正は確認表に残す。

金額入力は正の整数とし、符号を入力欄の外側に表示する。SplitEditorは種別を受け取り、円モードの符号と補足の配分金額へ反映する。%は無符号とする。清算の送金指示・履歴は双方に共通の金額なので、formatYenによる絶対額と送金方向で示す。支払い時は「支払者」、収入時は「受取者」、一覧共通見出しは「支払者／受取者」とし、「区分」（個人／共有）と「配分割合」は両種別で統一する。

formatJstDateTimeはDateTimePrecision.Minute／Secondで表示精度を指定し（既定は秒）、Asia/Tokyo固定で、ホーム・清算履歴・清算済み明細では秒まで、スマートフォンの明細要約では分まで表示する。CSVの元日時と定期支払いの日付表示は各画面で保持する。表示関数はdatetime-local入力には使わない。明細編集のtransactionDateInput／transactionDateToIsoは秒・ミリ秒を保持し、UTCへ変換する。新規明細の入力初期値は専用formatterを再利用して分まで表示する。

新規明細

NewTransactionModalはPAYMENTまたはRECEIPTを登録する。初期値は支払い・共有・現在のデフォルト割合で、支払い時だけ取引先ルールを適用する。新規収入の区分・割合初期化と保存経路は後述の「支払い・収入の追加と種別変更」に従う。登録成功でフォームを閉じ、保存失敗では入力を保持する。

定期支払いの取得・変更・実行

設定表示時にGET /api/recurring-payments?workspaceId=UUIDを実行し、payments、eligibleActorUserIds、日本時間のtoday、サーバー時刻のISO文字列nowを取得する。設定を既存bootstrapへ混在させず、full/metadataの通常2 SQLを維持する。現在の設定と次回予定を返し、開始日・適用月・変更予約・成功月はDTOへ含めない。

ワークスペース設定では集計用カテゴリの次、デフォルトルールの前に定期支払いを配置する。追加・編集フォームと一覧に開始日の項目は設けない。

同じURLのPOSTはactionごとのstrict schemaで検証する。createはworkspaceIdと設定8項目だけを受けて201、updateはworkspaceId、paymentId、expectedRevisionと設定8項目を受けて200を返す。設定項目はdayOfMonth、merchant、method、amountYen、actorUserId、expenseClass、splitWeights、memo。開始日を保存・管理せず、クライアントのstartOn・適用月・変更予約指定は400で拒否する。pause/resume/archiveはworkspaceId、paymentId、expectedRevisionだけを受ける。応答はpaymentだけを返す。

編集は設定8項目を現在の列へ即時に保存する。停止はACTIVE→PAUSED、再開はPAUSED/BLOCKED→ACTIVEに即時反映する。追加・編集・再開時には、設定日とtarget_nowから日本時間09:00を境に処理予定日next_scheduled_onを再計算する。設定日の変更による月内の複数登録を許容し、成功月は参照しない。削除はARCHIVED。生成済み明細は設定編集では変更しない。

未認証401、非所属/利用不可403、対象なし404、入力不正400、revision・状態の競合409、DB障害503を固定のerror/codeで返す。所有者・参加者はどちらも操作でき、設定保存・再開の本人を実行承認者にする。支払者・正の割合を持つ参加者の有効状態と認証モードも検証し、不明な参加者を勝手に削除・再配分しない。

GET /api/cron/recurring-paymentsはCRON_SECRETのBearer認証、任意日時/対象指定の拒否を行ってから実行する。POST /api/recurring-payments/runは非ProductionのAUTH_MODE=testだけで利用可能。本人の所属するworkspaceIdだけを受け、日時上書きは不可。Production/Googleモードでは認証・DBの前に404。両実行APIは登録失敗や時間制限による未処理があれば503を返す。

画面の次回予定の共通関数nextScheduledOnへ設定とサーバー時刻を渡す。当月の設定日を計算し、その日の日本時間09:00より前なら当月、09:00以降なら翌月の設定日を返す。存在しない日は月末へ補正し、ACTIVE以外はnullを返す。追加履歴やDBの成功月は参照しない。たとえば10/9に10日指定なら10/10、9日指定なら08:59まで10/9、09:00以降は11/9となる。フォームもAPIのnowを使用し、端末の時刻・タイムゾーンに依存させない。画面を開いたまま09:00を迎えた場合はサーバー時刻と受信後の経過時間から再取得し、一覧と開いたフォームの予定を更新する。フォームの入力は保持する。追加・編集・停止・再開・削除の成功時はフォームを閉じて一覧へ反映し、操作結果の通知枠は設けない。再取得時に削除済み・状態変更を検出した場合も通知文を表示せず、該当フォームを閉じて最新の一覧を表示する。取得失敗・保存失敗・revision競合のエラーと再試行操作は保持する。

DBの処理予定日はcake_recurring_next_scheduled_on(day_of_month, target_now)で同じ09:00境界から求め、追加・編集・再開時に保存する。候補はACTIVE、next_scheduled_onが日本時間の当日以前、現在のday_of_monthから求めた当月の予定日が当日、target_nowが当日09:00以降の設定に限る。指定日がない月は月末に補正する。ロック後に同じ条件を再確認し、通常のPAYMENT/RECURRING明細のINSERTとnext_scheduled_onの翌月への更新を同一Transactionで確定する。通常の同時実行・再呼出しや明細削除だけでは二重追加しない。開始日・適用月・変更予約・last_generated_monthは予定判定・生成に使用しない。取引日時は登録処理開始時のtarget_nowを使う。同じ実行の候補抽出と全明細生成に同じ日時を渡し、たとえば2026/10/27 09:23 JSTに実行すると保存・APIでは2026-10-27T00:23:00Z、編集欄・一覧・ホームでは日本時間09:23と表示する。生成済み明細は更新しない。外部IDはrecurring_{設定UUID}_{YYYYMMDD}_{明細UUID}で、設定変更後の月内複数登録も保持できる。

承認者・支払者・正の割合の利用不可などはBLOCKEDと固定理由を保存する。通信/DB障害では明細・処理予定日をすべてrollbackし、その呼出しでは再試行しない。翌日は翌日の予定だけを処理し、過去分は追加しない。未処理の予定日が残っていても、翌月の指定日にはその月の明細だけを追加する。時間制限は240秒で新しい処理の開始を止め、未処理を記録する。実行開始・設定ごとの結果・終了をrecurring.*ログへ記録し、取引内容や秘密値を含めない。

Productionは通常利用者のみ、非Productionのtestモードは固定テストID/メールの組だけを処理する。候補抽出では利用停止した承認者も検知できるよう、identityとenabledを分ける。実行時に利用可否を確認してBLOCKEDへ移し、自動実行でテストユーザーを再有効化しない。Cron設定はUTC 0 0 * * *、日本時間09:00ごろ。Hobbyでは09:00〜09:59のように実行時刻に幅がある（Vercelのスケジュール精度）。

Productionでは16文字以上のランダムなCRON_SECRETをVercelの環境変数へ設定し、Git・PR・ログへ保存しない。未設定・Bearer不一致のリクエストは401で拒否する（VercelのCron認証）。Previewには定期実行を期待せず、テストログイン中にPOST /api/recurring-payments/runへ{ "workspaceId": "対象UUID" }を送って当日予定を検証する。設定日の09:00以降に新規保存した設定は翌月予定のため、当日分は追加しない。

開始・登録成功・省略・失敗・終了はrecurring.*の構造化サーバーログで確認する。失敗は固定エラーコードと対象設定IDで確認し、金額・取引先・メモ・SQL本文・認証情報は記録しない。「要確認」は利用不可などで停止した設定で、原因を修正して再開する。過去の未登録分は通常の明細追加で登録する。アプリ内に共通ログ画面は設けない。

ホームの月次表と共有費配分の表はtable-layout: fixed、金額と参加者名はoverflow-wrap: anywhereとし、次の清算の送金方向・金額も縮小・折り返しを許可する。桁数の多い金額がページ全体を押し広げてスマートフォンの下部ナビゲーションを妨げないようにする。

明細編集・一括操作

  • 文字・日時・金額・割合は欄を離れるかEnterで保存。種別・支払者／受取者・区分などの選択項目は変更時に保存。既存明細の種別だけの変更では保存済みの区分・配分割合を保持する。清算済みの種別・金額・割合は編集不可。入力検証後、保存キューで順番に実行し、失敗時の下書きと再試行を保持する。
  • 明細・ルールの保存はlib/client/autosave.tsで要求集約・値比較・確定値追従を共通化する。Enter直後のblurは進行中の要求に集約し、キュー実行時に最新下書きと確定値を比較して同値のPOSTを省略する。確定値と下書きの反映をキュー内で完了してから次を実行する。保存中の追加編集は保持し、失敗時は自動再送せず入力を残して再試行する。日時の未確定入力、メモの独立保存、明細のfreeze/flushは各エディタで管理する。遅れたReact反映の間だけ確定値を補い、反映完了後の外部更新を受け入れる。
  • 取引の担当者を変更すると個人費の割合は新担当者1・ほか0に追従。共通費の保存済み割合は保持する。区分を新たに共通費へ変更すると現在のデフォルト割合を使う。
  • 割合は%と円入力を切替可能。円表示は最大剰余法で配分し同率時は参加者順、合計を整数円に一致させる。円入力は分担金額を重みとして保存する。
  • SplitEditorの単位プルダウンは共通部品で常に「%」「円」「1:1」の3択を表示し、呼出元ごとの表示可否フラグは持たない。明細追加・一覧・CSV取込・定期支払いの追加/編集で同じ選択肢を使う。二人参加中で編集可能な共通費に限り、選択すると二人の重みを1ずつに設定し、%表示の50%ずつへ戻す。新規明細では手動調整としてルールの自動適用を止め、一覧では変更した割合を即時保存キューへ送る。奇数円でも保存割合は1:1を保持する。個人費・清算済み・参加者一人では利用不可とし、CSV取込では対象行のプレビューだけを変更し、取込実行時にsplitWeightsとして送信する。未選択の登録可能行も編集でき、選択状態・他行・workspaceのデフォルト割合を変更しない。エラー行・重複行・保存中はfieldsetを無効化する。定期支払いではフォームのconfigと手動調整状態を更新し、追加/変更の保存時に専用APIへ送る。onChangeがない参照用と参加者一人では1:1のoptionを無効にする。workspaceのデフォルト割合入力は単位プルダウンを持たない。API・DBの変更は不要。
  • メモは空文字で削除可能、改行/空白を保持し最大2000文字。blurまたはCtrl/⌘+Enterで専用保存。清算済み行はメモとカテゴリを専用保存で編集できる。
  • 列を絞り込んでも未清算行の選択を保持する。編集・保存・エラー中の行は条件外になっても表示を維持。一括操作の前に未保存の変更を保存し、確定した取引先と担当者へルールを適用する。
  • 一括削除/ルール適用は選択全件の存在と未清算をDBで確認し、対象の一部だけを変更しない。ルール適用は支払いだけに許可し、収入を選択中は画面の実行を無効にする。DBでも対象全件のロック後に種別を検証し、収入が混在すれば全体を失敗させる。支払いでルール未一致は個人へ戻る。適用済み明細の確定値を応答し、編集Stateにも反映する。

SplitEditorは明細追加・一覧編集・CSV取込・ワークスペースのデフォルト割合で共用する。割合・配分金額の入力欄にはrequiredを指定せず、削除後の空欄を表示として保持し、計算と保存には数値0を使う。初期値の0と明示的に入力した0は0を表示する。単位の切替、明細金額の変更、親からのルール・区分の再適用では空欄表示を解除し、新しい値に追従する。相手の残額の自動計算、割合の0.1%単位、整数円、既存の数値範囲と全員0の拒否は維持する。

ルール編集

有効なルールを上から評価し、取引先の部分一致が最初に成立する一件を使う。文字・割合はblur/Enter、区分・デフォルト利用・有効状態は即保存。追加は末尾、ドラッグまたはスペース/上下キーで並び替え、選択したルールをまとめて削除する。操作キューは並び替え・削除と行編集を直列化し、失敗した入力や構造操作の再試行を保持する。ルール変更だけでは保存済み明細を変更しない。

orderedWorkspaceRulesはID→ルールのMapと出力済みIDのSetを用い、楽観的な順序に現在存在するルールを一度ずつ配置する。未知・外部削除済みIDは除外し、外部追加は最新取得順で末尾に残す。順序保存の成功時は最新取得順へ戻し、失敗時は操作前の順序へ戻す。選択IDの所属判定にもSetを使う。取引先の部分一致・優先順によるルール適用判定は変更しない。

PC取引明細の折り返し

TransactionTableのwrapを取引明細だけで有効にする。表のラッパーをinline-size containerとし、PC幅（48rem超）かつ表示領域90rem未満では明細行をflex-wrap、各セルを項目別の幅を基準に配置する。日時・割合・カテゴリ・メモの入力幅を確保し、既存のdata-labelを項目名として表示する。見出しのフィルタと全選択も折り返し、保存中表示・全幅のエラー行・カテゴリ色線を維持する。幅変更はCSSだけで切り替え、入力部品の再生成やデータ取得・保存は行わない。90rem以上の列別テーブル、48rem以下の要約と詳細展開、CSV取込と定期支払いの表示はそれぞれの既存レイアウトを使う。

取引明細のフィルタ保存

TransactionsPanelはuseTransactionFilters(userId, workspaceId)で列ごとの条件を管理し、lib/client/transaction-filter-storage.tsを通してlocalStorageへ保存・復元する。API・DBへは保存しない。

保存用の列条件は文字列配列のまま保持し、条件または参加者の変更時にcreateTransactionFilterMatcherが列ごとの検索用Setを準備する。同じ列はOR、列間はAND、空選択は0件とする。transactionListViewは各明細の条件を一度だけ判定し、編集中・保存失敗・メモ編集中の条件外行を含む表示と条件外表示の印で結果を共用する。表示ID・未清算ID・選択IDの所属をSetで照合して非表示選択数と全選択状態を求め、削除済み・清算済みIDは一括操作対象から除く。絞り込みでは非表示の選択を保持する。

条件の意味種別はPAYMENT／RECEIPTの値で絞り込む。金額候補はPAYMENT:1000／RECEIPT:1000のように種別と正額を組み合わせ、−¥1,000と+¥1,000を区別する。列IDの省略はその列の絞り込みなし。空配列はすべての候補を未選択にした条件として保持し、該当明細を0件にする。全列の絞り込み解除でオブジェクトが空になった場合は保存キーを削除する。
復元・更新保存キーのv1を維持し、旧形式の金額条件である符号なし数字文字列は復元時にPAYMENTとRECEIPTの両候補へ展開して、同じ正額の両種別に一致する意味を維持する。その他の列条件は保持する。ユーザーIDまたはワークスペースIDの変更時に保存先を切り替える。画面再表示・再読み込み時に保存値を読み、変更時は即時保存する。useSyncExternalStoreのサーバー描画時の初期値は空オブジェクトとし、ブラウザで復元する。同じブラウザの別タブによる変更・削除はstorageイベントで再読込する。

保存範囲同じサイトのブラウザ内だけに保持し、別端末・別ブラウザへ同期しない。サイトデータの削除で保存条件を初期化する。

8. ドメイン処理詳細設計

保存割合・デフォルト判定

SplitWeights = Record<userId, number>は現在の参加者IDをすべて含み、余分なIDなし、各値0〜2147483647の整数、合計は正とする。validateSplitWeights()は入力のコピーを返す。個人費はactorが1・ほか0、共通費は任意の有効割合を保存する。

prepareDefaultRuleMatcher(rules)は有効なルールだけを新しい配列へ抽出し、sortOrder昇順の安定ソートを一度行って、先頭から最初に部分一致したルールを返す判定関数を作る。同順位は入力順を維持し、入力配列を変更せず、未整列入力も受け付ける。transactionDefaults()は準備済み判定関数を一度呼び、区分と割合を返す。CSV解析はファイル全行、取込APIはリクエスト内の全明細で一つの判定関数を共有し、支払いの単件登録も同じ方式で準備する。収入保存は支払いルールを取得・判定せず、区分未指定はPERSONAL、SHARED指定かつ割合未指定は現在のデフォルト割合を使う。更新時は保存済み区分・割合を先に継承する。明細追加・定期支払いフォームはルール一覧を依存値にしたuseMemoで準備し、取引先の変更や再描画で再ソートせず、一覧更新時に作り直す。グローバルなルールキャッシュは持たない。未一致は既定PERSONAL、明細追加・定期支払いの共有workspace・CSV取込ではSHAREDフォールバックを指定する。共通費のルール割合nullはmemberの現在デフォルトをコピーする。明示ルールの新参加者IDがない場合は0として補う。個人費は担当者1・ほか0とし、デフォルトやルール変更だけでは過去明細の保存割合を変更しない。

支払い向けルールはCSV・手動支払い・定期支払いに適用する。cake_bulk_transactionsのAPPLY_RULESは、ロック中の対象にRECEIPTが1件でもあれば全件を失敗させる。DELETEの対象種別は制限しない。

PayPay CSV解析

清算計算

calculateSettlement(members, transactions): SettlementResult | null

  1. メンバーがちょうど2人でなければnull。未清算のSHARED明細だけを抽出し、0件ならnull。
  2. 対象actorの所属、正の安全整数金額、各明細の保存割合を検証する。
  3. 支払いを正、収入を負として正味共通費を計算。各明細の金額に、その明細の先頭参加者割合を掛けた分数をBigIntで正確に合算する。
  4. 全明細を合算した先頭参加者の負担を一度だけMath.round相当で丸める。負の0.5も正の方向に丸め、二人目の負担は正味共通費から先頭負担を引く。
  5. actual = ownPayments - ownReceipts、balance = actual - target。負balanceの人が支払側、正balanceの人が受取側で、送金額は負balanceの絶対値。
  6. 差額0ならpayer/payeeのID・名前はnull、金額0。対象明細があれば0円の清算完了も可能。
targetTransactions = SHARED && !settledAt signedAmount(t) = PAYMENT ? amountYen : -amountYen netTotal = Σ signedAmount(t) firstBurden = Σ [signedAmount(t) × t.splitWeights[firstId] / Σ t.splitWeights] (exact BigInt fraction) firstTarget = round(firstBurden) (once after aggregation) secondTarget = netTotal - firstTarget actual = ownPayments - ownReceipts balance = actual - target amountYen = abs(payer.balance)

SettlementPerson.weightとweight_snapshotは現在のデフォルト割合を記録するが、計算は各明細のsplitWeightsを使用する。清算Snapshotには対象明細ごとの保存割合も含める。

清算の内部計算は負担額の方向（支払いを正・収入を負）で保持し、表示だけを収支方向へ変換する。ホームの未清算の共有収支は-netTotalと同じ対象・符号で集計し、共有費配分の「現在の収支」は-actual、「配分後の収支」は-target、「精算額」はbalanceを表示する。精算額は清算で受け取る予定額を正、支払う予定額を負とし、formatCashflow・cashflowClassで符号と色を整える。0円は通常色とする。Aが共有収入10,000円を受け取り、割合が1:1ならAからBへ5,000円の送金となる。送金指示と履歴は方向＋正の金額で表示し、清算完了による送金取引を家計明細へ追加しない。

集約SQLと整数配分

本人の有効性確認1 SQLの後、集計storeは本人有効性・現在のworkspace所属・参加者・カテゴリ・集約を同じ1 statementで取得する。通常2 DB往復で、明細や人数に比例する通信を増やさない。GETは初期workspaceも作成せず、未認証401・未所属403・不正入力400・保存データ不整合や取得失敗500を返す。

対象は3範囲のいずれかに入る一意なPAYMENTとRECEIPTで、SHAREDまたはactor_user_id本人に限定する。相手のPERSONALは支出・収入とも保存割合検証・配分・集約より前に除外し、金額・件数・不正割合のエラーを漏らさない。清算状態・source・カテゴリ確認状態にかかわらず取得する。保存split_weightsから整数商と剰余を求め、余り円を剰余降順・joined_at ASC, user_id ASCの順に配分する。全員の配分確定後に範囲へJOINし、重なった期間で配分前の明細を増やさない。個人費は担当者100%とし、不正な保存割合や担当者を黙って補正しない。種別ごとに集約し、支出のbucketsと収入のreceiptBucketsを混在させない。

現行のsplitAmountsと同じ明細ごとの整数円を合計するため、全員の負担額は支払総額に一致する。清算の「分数を全件合算して最後に丸める」計算とは目的・丸めの単位が異なる。清算の対象や保存結果は変更しない。TSとSQLの配分を共通fixtureで照合する。

SQLはUTCへ換算した境界に対するoccurred_at >= start AND occurred_at < endExclusiveを使い、workspace/date indexを利用できる形にする。金額と重みの積・除算・最終SUMは整数精度を保ち、集計額をSQL内でtext化する。取引先・明細ID・保存割合などの生データは返さない。事前集計テーブルや用途未検証のindexは設けない。

DTOと表示計算

本人モードはcaption付きの表に収入・支出・収支を3行で表示し、formatCashflowとcashflowClassで符号・色を統一する。収入のみ・0円も表を表示し、支出グラフが空であることと区別する。共有費全体では従来の3カードと支出グラフを維持する。本人モードの月次は収入・支出・収支を表示し、カテゴリ内訳と前期間差分は支出専用と説明する。本人チェックを概要と3グラフへ適用し、表示形式をAPIへ送らない。

AnalyticsDatasetはworkspaceId / snapshotAt / timeZone / periods / members / categories / buckets / receiptBuckets。bucketsは支出、receiptBucketsは収入とし、どちらもscope(current|comparison|trend) / month / memberId / expenseClass / categoryId / burdenYenの配列を必須で返す。金額は非負10進整数文字列で、0円のみの組合せは省略して欠落を0円として扱う。scopeを混在させず、月次の欠落月を0円で補う。prepareAnalyticsDataset()は両配列をBigIntへ変換し、buildAnalyticsView()が同じmemberIds・expenseClassesでcashflowの収入・支出・収支、比較期間と月次を算出する。既存のtotalYen・rows・chartRowsは支出だけを保持する。

参加者・カテゴリは金額と同じsnapshotの情報を使い、metadataの別応答を後から混ぜない。停止中の参加者、旧使用停止カテゴリ、未分類も取得対象に含む。現在の名称・階層・色で表示し、カテゴリの削除で参照解除された明細は未分類とする。親やrootへの対応表はdatasetの更新時に準備し、フィルタ変更時の祖先探索を繰り返さない。

AnalyticsFilters.categoryIdsは任意の元カテゴリID配列で、省略は全件、空配列は対象なし。未分類にはANALYTICS_UNCLASSIFIED_IDを使う。表示計算は階層別の集約や上位8件・その他へのまとめより前に、正規化済みの元カテゴリIDをSetで照合する。同じ選択を支出のbucketsと収入のreceiptBuckets、current・comparison・trendの全範囲へ適用する。子だけを選んで大分類へ表示しても、同じ親の非選択カテゴリは合算しない。カテゴリ選択によって合計・差額・率・構成比・月次・表が同じ対象から再計算される。

カテゴリ粒度は最上位、任意の途中階層、全階層。深い設定は祖先へ集約し、浅い親に直接設定された額を失わず、親集計と子を二重計上しない。全階層で親への直接設定は「直接設定」と表示する。比較元だけのカテゴリも差分に残す。図の共通系列は今回・比較元・各月の最大額順の上位8件＋その他＋未分類、同額はカテゴリ表示順・IDで固定する。一覧・表は集計対象の全カテゴリ。

円の描画時は共通系列のうち対象期間が正の項目を取り出し、その他・未分類も含め対象期間の整数金額の降順へ安定整列する。同額は共通系列の順を保つ。開始角90度・終了角−270度とし、12時から時計回りに表示する。他の図と一覧の系列順は変えない。円と棒の金額は領域内へ重ね、描画領域に収まらなければ省略する。月次棒は横置きを優先し、長辺方向に収まる場合は回転して表示する。金額ラベルは背景カテゴリ色に応じた白または黒の文字色で判読性を確保し、金額ラベルは操作を遮らない。中央合計も実際の内円へ収め、文字サイズと改行を調整する。12px以上で全桁を表示できない場合は中央の金額を省略し、画面上部の負担額で全桁を確認できる。円のコンテナは中間幅のgrid配置でも幅を確保する。

加算・差額・率計算はBigIntを使う。構成比・増減率は小数1桁で表示し、比較元0円は0÷0も含め率を算出しない。Rechartsへ渡すNumberは座標用だけとし、カテゴリ図の金額は元の整数値からformatYenで表示し、本人月次の金額はformatCashflowで符号を付ける。カテゴリ別支出の合計・表・ツールチップ・中央合計は符号なしの通常色で表示する。カテゴリ図の金額も符号なしとし、背景との可読性で文字色を選ぶ。本人の月次収支は後述の符号規則を使う。面積・積上げの座標と構成比は非負の金額を使う。前期間との差額はtotalYen - comparisonYenとし、支出増を正、支出減を負として通常色で表示する。差額に限って正は＋、負は−を付け、増減がない場合は無符号とする。API/表示計算の非負金額と差額の内部契約は保持し、率は支出の増減として説明する。ラベルが省略されても一覧・表とツールチップで全額を確認できる。複数人の個別件数を足した取引件数は表示しない。

月次収支とグラフの配置

両モードで月次→カテゴリ内訳→前期間差分の縦配置にする。AnalyticsChartsのcashflowTrendは本人モードだけtrueとし、cashflow.monthsの同じ6か月のincomeYen・expenseYen・balanceYenを使う。本人月次は収入・支出の並列Barと収支のLineを同一ComposedChartへ描き、表示額を10,000で割った座標を共通縦軸に使う。収支の負数を含めた最小値・最大値を整数へ外側に丸め、両端の目盛を表示する。棒は金額の大きさ、折れ線は収入−支出の正負を保つ。0円の月も期間から補い、月別表でも全額を示す。共有費全体は従来のカテゴリ別支出BarChartと表を同じ先頭位置に表示する。

収入は緑、支出は赤、収支は線と凡例でも区別する。Numberは座標だけに使い、棒の金額ラベル・ツールチップ・月別表は元のBigIntをformatCashflowで整形する。月次ツールチップはスマートフォンの横幅に収め、巨大額も省略や浮動小数化で値を変えない。ラベルは描画領域内に収まる場合だけ表示する。incomeYenがあるだけの期間は月次を描き、支出のドーナツが空であることと区別する。

取得・保存・遅延応答

集計panelは同じworkspace内のタブ切替でStateを保持する。同階層の条件付きpanelと識別子が衝突しないよう、Reactのkeyには画面種別とworkspace IDを組み合わせる。初回表示・再入場・期間変更・明示更新・保存後の無効化で取得する。本人チェックが全OFFでも期間取得は行い、その後ONへ戻して追加通信しない。取得中にcheckboxを変えても応答は保持し、最新の表示条件で描画する。workspace・期間・保存後世代・要求順が古い応答は破棄する。workspace切替中は旧グラフを非表示とし、切替先で条件を初期化する。切替後の別タブ取得により元の要求を破棄しても切替中を保持し、最新の取得が採用されたときだけ解除する。最新の取得が失敗した場合は以前のworkspaceへ戻して解除し、遅い旧応答を採用しない。

対象カテゴリはモード・区分・粒度・期間変更と同じworkspaceのタブ往復で保持し、workspace切替で全選択へ初期化する。全件状態では更新後の新カテゴリも含む。個別選択後は明示したIDだけを使い、新カテゴリを自動では追加しない。削除済みIDは現在候補との共通部分だけを選択済みとして扱う。全解除中も期間変更や更新の取得を止めず、選び直した時点の最新データへ同じ表示条件を適用する。

期間変更中は読込表示とし、旧期間のグラフを新条件の結果として見せない。取得失敗は選択を保持して再試行を表示し、0円の成功へ置き換えない。明細の未保存入力は含めず、保存成功後に世代を進める。グラフは遅延importし、未訪問タブでRechartsを読み込まない。PCホバー・キーボード、mobileタップ、全カテゴリの表を用意する。

取引先の照合用正規化

照合規則の正本はcake_normalize_merchant(text)とし、現行基準はPostgreSQL 18組込みのUnicode 16とする。関数はIMMUTABLE STRICT PARALLEL SAFEで、pg_catalog.normalizeのNFKCを適用後、pg_catalog.pg_unicode_fast照合順序を明示したlowerで小文字化する。その結果の連続空白を1個の半角スペースへ置き換え、前後のスペースを除去する。小文字化はUnicodeの小文字変換であり、case folding・ひらがなとカタカナの相互変換・記号除去・部分一致への拡張は行わない。

空白はECMAScriptのWhiteSpaceとLineTerminatorに相当する固定25コードポイント、U+0009〜U+000D, U+0020, U+00A0, U+1680, U+2000〜U+200A, U+2028, U+2029, U+202F, U+205F, U+3000, U+FEFFを使う。NFKC後にこの集合を適用し、U+0085とU+200Bは保持する。空文字・空白だけの入力の結果は空文字、NULL入力の結果はNULLとなる。入力の必須・長さ制約は既存schemaとDB制約を維持する。

transactions.merchant_normalizedはtext COLLATE "C" GENERATED ALWAYS AS (cake_normalize_merchant(merchant)) STORED NOT NULLで保持し、(workspace_id, merchant_normalized)のBtree Indexを設ける。NFKCによる展開後の値へ240文字の上限や切捨てを適用せず、例えば㌕240文字はキログラムの繰返し1200文字・3600バイトとして保存・Index登録する。通常の列値として直接指定せず、merchantのINSERT/UPDATEと同じDB処理で計算する。手入力・一覧編集・CSV集合INSERT・定期生成・seed・旧版の保存・直接SQLにも適用され、呼出元の指定漏れで照合用値が古くならない。表示用のmerchantと現在の公開API/DTOは保持する。区分のルールの部分一致、CSV内・既存重複の金額と取引先比較にも照合用値を流用しない。

専用DBの所有権照合 → migration → ユーザーseed ├─ カテゴリ表なし（baseline検証） → サンプル処理なし └─ カテゴリ表あり ├─ samples_seeded_atあり → 既存データ保持 └─ 未完了 → 対象表lock → 初期状態と空データを照合 ├─ 一致 → カテゴリ10件 → 明細8件 → 完了marker └─ 不一致 → 追加を省略 → 完了marker サンプル判定・登録・marker更新は同一Transaction。失敗は全体rollback。

scripts/db/setup-db.mjsは環境に応じたDB接続（PreviewはCAKE_TEST_DATABASE_URL、それ以外はDATABASE_URL）を確認する。台帳初期化を1回実行し、schema_migrationsの履歴を一度読みSetで照合して、未適用SQLの本文だけをファイル名順に読み込む。全適用済みの通常再実行は本文0読込・2往復、未適用がN件なら本文N読込・N+2往復となる。各SQLは共通advisory lock取得後に台帳を再確認し、SQLと履歴INSERTを同じDO文/Transactionで確定する。同時実行や失敗時にも二重適用・台帳だけの記録を防ぎ、既存データや適用日時を保持する。

Previewでは接続前にendpoint等の環境情報とmigration名・番号順を検証する。既存markerの照合と台帳初期化を同じDO文へまとめ、所有権・世代不一致は停止する。marker欠落のSQLSTATE P0001と固定エラー文面が一致するときだけ、失敗したDO文の全体rollback後に初回処理へ進む。初回は全migrationの原文・承認済み001〜011のhash・002の本番bootstrap除去を確認してから、空DBまたは承認済みfixtureのDB照合・marker確保・台帳初期化を行う。この初回経路は追加の検査を要するため、通常再実行の2往復とは区別する。既存同一世代では適用履歴を使い、未適用分の原文だけを検証する。repository全体の承認済み原文照合は回帰テストでも維持する。

006_paypay_external_ids.sqlはsource = PAYPAYの既存外部IDを、保存済みoccurred_at AT TIME ZONE 'Asia/Tokyo'から生成したPayPay_YYYYMMDDHHMMSS_{取引番号}へ移行する。すでに新形式の外部IDと手動明細は変更しない。UUID主キーと参照関係は保持し、キー衝突時は一意制約で移行全体を失敗させる。移行前に日時を編集していた明細は元のCSV日時を復元できないため、再取込時の重複判定が一致しない場合がある。

移行中はtransactionsへの書込みをロックして、既存データの変換と登録時トリガーの作成を一体で適用する。cake_normalize_paypay_external_idを呼ぶBEFORE INSERTトリガーは、更新切替中に旧サーバーが送るPayPayの取引番号だけの外部IDも新形式へ変換する。手動明細と新形式は保持し、UPDATE時には実行しないため日時編集後も元の外部IDが残る。

現行コード上の権限境界

  • workspace更新は招待承認を除き所属を確認。actorは同じworkspaceの参加者であることを追加検証。
  • 招待は本人のログインメールと宛先の一致を確認し、平文tokenは保存せずSHA-256を保存する。招待承認だけでは未登録Googleユーザーの利用許可を与えない。
  • 所属者はOWNER/MEMBERによらず名称・招待・割合・ルール・明細・清算・workspace削除を操作できる。削除は名称一致と確認ダイアログを使い、再認証は行わない。
  • 利用者管理は現在のDBで有効な管理者のみ。固定テストではQA identityを照合したAだけ許可する。管理者の停止は拒否し、停止済み通常ユーザーの再登録は既存内部IDとデータを保持。

開発・Preview管理の契約

常設Previewは staging.yml・staging-service.ts・staging-workflow.ts・staging.config.jsonで管理する。mainのpush/dispatchのみ受け付け、GitHub contents:writeは予約branch cake-main-previewの作成とfast-forwardだけに使う。予約名のbranchがmain履歴上のancestorである場合だけfast-forwardし、分岐したbranchは上書きしない。初回mirror作成後、Deployment未作成のままmainが進んでも、DBだけが残っていなければ同じ規則で復旧できる。mainやPR branchは更新しない。通常PRの正整数IDと区別するため、CAKE_PREVIEW_KIND=main・PR予約値0・固定branchの組合せだけを許可し、既存DB markerのpr=0に常設所有権を保持する。Nativeの準備→application・本番host分離・世代照合・初回だけのA/B seedを共用する。StagingProviderはmainとmirrorの完全SHAを各操作前後に照合し、PR APIとclosed状態を拒否する。常設DBをPR cleanupへ渡さない。Vercel認証保護、PC/mobile A/Bのログイン・画面移動・session/app GET・runtime proof、前後statusを確認後、同projectで管理されたaliasだけを更新する。結果は独立した cake-staging/v1 noticeで返し、PR Ready用証拠としては扱わない。

実装はCake内のpreview-command/provider/service/workflow/receipt/checks/browser/readyとpreview.config.json。mainのpreview.ymlのみがprovider管理資格情報を使用し、PRごとのconcurrencyで直列化する。同一repositoryのcodex/*からmainへのPRのopened/synchronize/reopenedで自動deployし、closedでcleanupする。管理側はmainの完全SHAだけをcheckoutする。自動deployのoperation UUIDはrun IDから決定し、rerunでも同じ操作として照合する。古いHEADのイベントはprovider書込前に拒否する。Vercel Git連携のfeature deployを停止し、専用DBのprovisioning→applicationと所有権guardを維持する。closedイベントでもmainのみをcheckoutし、featureコードを管理資格情報付きで実行しない。configのreceiptTransport: github-actions-notice/v1を含む完全一致をdispatch前に確認し、旧main未導入ではPREVIEW_NOT_INSTALLED_ON_MAINで停止する。dispatchの必須input controlShaでCLIが固定したmain SHAを渡し、workflow開始時のGITHUB_SHAと異なればprovider操作前に停止する。main更新との競合でも別SHAの操作を続けず、盲目的に再dispatchしない。provider protocol cake-preview/v1とDB marker version 2は維持する。

公開用receiptにrunId・runAttempt・controlSha・operationを付け、compact JSONが4,096 UTF-8 bytes以下であることを送出前に検査する。provider操作後のローカルpreview-result.jsonを専用step Publish public operation receipt noticeで再検査し、固定title cake-preview-receipt/v1の標準noticeを1件出す。本文の%・CR・LFをworkflow command用にescapeする。runnerの秘密マスク・切詰めを受けた内容は受理しない。noticeはログにも残るため非秘密projectionだけを送る。artifact upload/download、外部relay、checks: writeは使わない。

CLIはworkflow ID/pathと対象runのrepository・event・main ref/SHA・初回attempt・successを固定し、attempt指定jobs APIの全ページから唯一のpreview jobを選ぶ。canonical check_run_urlからCheckRun/CheckSuiteのrepository・head SHA・GitHub Actions appを照合し、全annotationから固定titleのnoticeを正確に1件だけ受け入れる。重複keyを含む不正JSON、欠落・重複・古いattempt・マスク・切詰め、PR/HEAD・operation・run ID/attempt・control SHA・時刻の不一致は停止条件。取得後にrun/check metadataと件数を再確認し、receiptはGit外の.cake/preview.jsonへ保存する。この照合は更新の検出であり、永続不変や暗号学的署名の保証ではない。

Actions verifyの独立契約

qa:verify:ciは対象PRのHEADとは別のcontrol checkoutから動く。control側はcleanでHEADが取得時点の最新mainに一致し、対象はOPEN・同一repository・専用branch・完全SHA・READY application Deployment IDに固定する。mainのpreview-verify.config.jsonを{protocol: "cake-preview-verify/v1", workflow: ".github/workflows/preview.yml", action: "verify"}と照合してからdispatchし、旧mainのverify未導入を止める。既存3 actionのwire/title/schemaとpreview.config.jsonを変更しない。verify用inputは対象deploymentIdを持ち、operation/controlShaで正確な要求を結び付ける。

同じmain限定workflow/concurrencyを使い、mainの完全SHAだけをcheckoutする。verifyの場合のみ資格情報を渡す前に公式npx playwright install --with-deps chromiumを行う。provider TransportはmethodがGETでbodyなしのものだけを下流へ渡し、Vercel development env取得のOIDC読取にも同じguardを使う。既存VERCEL_TOKEN・NEON_API_KEY・読取用github.tokenだけを使用する。status前照合→通常TLSブラウザ検証→status後照合で対象とDBの不変を確認し、provider作成/更新/削除、direct SQL、migration、seedの入口は呼ばない。新規auth/security/network設定を必要としない。

verify専用receiptはprotocol/titleともcake-preview-verify/v1で、成功と固定stage/codeの失敗を区別する。送出前に公開項目と4,096 UTF-8 bytes上限を検査し、PR/HEAD/Deployment/DB・case/クリック/観測時刻とrun/初回attempt/control SHA/operationを照合する。既存noticeと同じ厳密JSON・全annotation取得・run/job/check/suite/repository/appの来歴検査を行う。成功receiptはcompleted/successと一致するものだけ受理し、失敗receiptはcompleted/failureと一致する診断だけを受理する。生例外、token、Cookie、接続文字列は含めず、欠落や不一致では停止する。artifactを結果輸送に使わない。

成功証拠のcontrol側.cake/verify-<PR>.jsonはprotocol cake-preview-remote-proof/v1、workflow ID、受理済みverify receiptを保持する。検証CLIからPRをReadyにはしない。新CLIを含む対象PRでは、完了条件を確認したCodexがtask:pr --remote-proof <path>を実行し、現在HEADのCIと保存receiptのActions来歴を読み直してReadyにする。別の対象PRには最新mainのcontrol checkoutから--remote-proof <path> --target-worktree <path>を使い、対象ブランチのコードを変更・実行せずGit/gh管理を行う。target指定はremote proof必須・非draft専用で、controlのcleanな最新main/verify capabilityと対象のcleanな専用branch/完全HEADを照合する。変更説明・報告書・証拠・対象worktreeのpathはcontrolのCWD基準で、絶対pathを推奨する。省略時のローカル証拠と既存Ready動作は変えず、異なるPR/HEAD/Deploymentの証拠は拒否する。

資源とブラウザの共通照合

lib/server/database/production-database-hosts.mjsが設定のproductionHostDigest（現用値）とproductionHostDigests（現用PG18・保持旧PG17のPreview禁止集合）を検証する。集合は現用値を含む非空・重複なしの64桁hexとし、省略時だけ現用1件に補完する。接続前guard、provider、Deployment metadata、通常/verify receiptは同じ集合全件を拒否する。runtimeは従来の環境側本番digestとDATABASE_URLのendpoint一致拒否も維持する。準備用buildと実DBQAの注入本番digestは、対象コードの集合への厳密な所属を要求する。現用値をPG18へ更新した後も保持旧PG17のdigestを集合へ残し、どちらのDBもPreviewとして受け入れない。禁止集合は対象コードから読み、環境側の値だけを正本にしない。

現用本番はNeon PostgreSQL 18・UTF8の専用projectを使い、Vercel NativeのProduction接続から供給されるDATABASE_URLを使用する。旧PG17 DBと既存の復旧用branchは保持する。Productionのbuild:vercelはNext build後に通常のdb:setupを行い、各migrationと台帳の記録を同じTransactionで確定してから公開する。テストseedは実行しない。019の取引先正規化と、専用Previewでの通常の実DBQAは継続する。

本番DBの版更新・復旧では、対象とバックアップ、最新データの同期方法、ProductionのNative接続先を確認する。接続変更後は新しいProduction Deploymentを作成し、公開先・完全SHA・接続先と本人Googleログイン・既存データ表示を確認する。書込み開始後の復旧では追加データの保持と同期も確認する。現用本番・保持旧DB・復旧用branchの識別情報と手順は本番DB運用手順を参照する。

Deployment metadataのprotocol・repository・PR・generation・operation・phaseとGitSourceの完全SHA・branchを全ページ一覧と直接GETで照合する。初回provisioningはDBに接続せず、対象PR・branch/SHA・世代・本番host digestと空の専用DB識別子を検査した後、Build Output API v3の静的準備中ページを.next/outputへ生成する。既存のNext.js builderで正常終了させ、API・ログイン・POSTは404とし、アプリのFunctionや環境値を成果物に含めない。通常アプリのbuild前には.next/outputと.vercel/outputを除去し、準備成果物の混入を防ぐ。準備用のREADYだけではstatusのapplicationと扱わず、新たな準備用のERROR/CANCELEDは管理処理を停止する。Native子branchの親・作成時刻・所属・非保護・read-write endpointを確認後、IDとhost digestをapplication deploymentへ渡す。初回の作成時刻下限はsource作成時刻と最古Deploymentの要求時刻（時計差60秒）から求める。単一世代の既存applicationがDB branch・endpoint・host digestを保持する更新では、source作成時刻だけを下限とし、現在残るDeploymentの作成時刻で継続DBを拒否しない。既知DBも親・所属・保護・単一endpoint・本番分離と一覧／直接GETの一致を再確認する。接続文字列はNativeが供給する。

DB識別marker version 2はrepository・PR・generation・source branch・Native branch・host・database名を保持する。DB接続前にURL上書きparameterと本番endpoint一致を拒否し、migration/seedは排他guard下で所有権を照合する。同PR更新ではmarkerとseed済みデータを保持する。旧markerは移行・上書きしない。

GET /api/qa/previewはPreview/test限定で、実アプリと同じDB clientのmarkerを読取照合しnonce・commit・Deployment・DB digestを返す。任意のfeatureコードの暗号学的証明ではない。ローカル/Actionsは同じブラウザhelperで通常TLS通信とorigin限定OIDCを使い、PC/mobile A/Bの16実クリック・session/app GET・runtime proofを確認する。各caseでruntime-before・session/app・runtime-afterの観測時刻を記録する。HTTPはGET/HEAD/OPTIONSと認証callback POSTを許し、redirectの各hopを対象originへ制限する。ただし既存GET /api/appはworkspace0件なら初期workspace/membershipをINSERTするため、HTTPの制限をDB完全無変更の保証にしない。アプリ変更では検証前後のprovider照合・現在HEADのブラウザ証拠・最新push/PR CIと差分レビューがReady条件。文書のみの変更は開発手順の文書検証・CI・Preview/status照合に従い、再検証を省略する理由を記載する。証拠はGit外の.cakeに保存する。

cleanupはclosed PRを削除直前にも確認し、metadataを持つ最後のDeploymentを復旧用に残して他Deployment・専用DBを削除する。Nativeの先行削除も直接GETで確認し、最後のDeploymentと全資源の不在後だけ完了にする。応答不明時は同じrunのmetadataを再照合し、盲目的なPOSTをしない。実資源操作は対象と影響が承認された範囲で行い、PRのmerge/closeが削除を起動し得ることを確認する。無断でPRを閉じない。PR専用資源だけを対象とする。
